# 旧版定时任务分析

> 分析范围：`旧版源码/com/ruoyi/system/task`。
>
> 说明：各任务类仅标注了 Spring `@Component`，未见 `@Scheduled` 注解。因此，这些类提供的是可被调度框架调用的任务入口；实际的触发频率、Cron 表达式及启停状态，仍需从 Quartz 配置、定时任务配置表或后台任务管理代码中确认。

## 一、任务总览

| 任务类 | 执行方法 | 主要作用 |
| --- | --- | --- |
| `SynAccountGenerateTask` | `SynAccountGenerate()` | 为车辆业主自动生成系统登录账号 |
| `SynAreaInfoTask` | `SynAreaInfo()` | 从外部平台同步停车区域，写入系统字典 |
| `SynCarCapInfoTask` | `SynCarCapInfoList()` | 同步车辆进出场记录 |
| `SynCarListTask` | `synCarList()` | 从外部平台同步固定车位车辆信息 |
| `SynHikUserTask` | `SynHikUser()` | 从海康门禁设备同步用户及人脸信息 |
| `SynVioBlackTask` | `SynVioBlackList()` | 设计上用于同步违章黑名单，但当前实际为空操作 |
| `SyVioDischargePunishmentTask` | `dischargePunishment()` | 到期解除车辆违章黑名单处罚 |

## 二、逐个任务分析

### 1. `SynAccountGenerateTask`

**入口方法：** `SynAccountGenerate()`

#### 主要流程

任务遍历本地车辆信息：

```java
for (CarInfo carInfo : carInfoMapper.queryCarInfoList()) {
    SysUser userByPhone = sysUserMapper.getUserByPhone(carInfo.getTel());
    if (userByPhone == null) {
        // 创建系统用户
    }
}
```

以车辆联系电话 `carInfo.getTel()` 查询系统用户；若不存在账号，则创建新的 `SysUser`：

```java
sysUser1.setDeptId(229L);
sysUser1.setUserName(carInfo.getTel());
sysUser1.setNickName(carInfo.getUseName());
sysUser1.setPassword(SecurityUtils.encryptPassword("Fqjg20221022"));
sysUser1.setPhonenumber(carInfo.getTel());
sysUser1.setStatus("1");
sysUser1.setRoleIds(new Long[]{104L});
userService.insertUser(sysUser1);
```

#### 业务目的

为固定车位车辆使用人自动开通平台账号，通常以手机号作为登录名。

#### 创建账号规则

| 字段 | 值或来源 |
| --- | --- |
| 部门 | 固定为 `229` |
| 用户名 | 车辆联系电话 `tel` |
| 昵称 | 车辆使用人 `useName` |
| 手机号 | 车辆联系电话 `tel` |
| 初始密码 | 固定为 `Fqjg20221022`，存储前加密 |
| 状态 | `"1"`，具体启用/停用含义需按项目字典确认 |
| 角色 | 固定角色 ID `104` |

#### 风险与注意点

1. 初始密码硬编码，且所有自动创建的用户共用密码，存在安全风险。
2. 固定部门 ID、角色 ID 依赖初始化数据；数据变动时可能归属错误。
3. 以手机号判断唯一性，电话号码为空、重复或多人共用时可能出现问题。
4. 未见车辆与用户之间的显式关联字段，仅通过手机号间接关联。

### 2. `SynAreaInfoTask`

**入口方法：** `SynAreaInfo()`

任务入口本身只委托给：

```java
areaInfoTaskService.SynAreaInfo();
```

实际逻辑位于 `AreaInfoTaskServiceImpl`。

#### 主要流程

1. 调用科拓停车平台区域接口：

   ```java
   HttpAPI.getParkingPlaceArea
   ```

2. 使用服务编码、基础请求参数和签名组织请求：

   ```java
   Tools.packBaseReq(HttpAPI.getParkingPlaceAreaServiceCode);
   SignUtils.paramsSign(...);
   ```

3. 从响应中读取 `areaInfo` 数组，解析为 `AreaInfo`。
4. 将区域信息同步到系统字典表，字典类型为 `area_type`。

#### 写入规则

以“字典类型 + 区域编码”查询：

```java
getDictDataByTypeAndValue("area_type", String.valueOf(area.getAreaCode()))
```

- 已存在：更新字典标签为最新区域名称；
- 不存在：新建字典数据，区域编码为 `dict_value`，区域名称为 `dict_label`。

#### 业务目的

将外部停车平台的停车区域同步为系统可使用的区域字典，为车辆车位归属、区域下拉选择和违章车辆区域调整等功能提供基础数据。

#### 风险与注意点

1. 仅新增或更新，未处理外部已删除或停用的区域。
2. 外部接口失败时没有重试、告警和失败记录。
3. 使用 `System.out.println` 输出完整结果，不利于生产日志管理。
4. 创建人固定为 `admin`，无法准确追溯同步来源。

### 3. `SynCarCapInfoTask`

**入口方法：** `SynCarCapInfoList()`

#### 主要流程

先查询本地最后一条车辆进出记录：

```java
CarCapinfo lastCarCapInfo = carCapinfoService.getLastCarCapInfo();
```

- 若有记录：以最后记录的 `capTime` 作为 `startTime` 增量同步；
- 若无记录：传入 `null`，执行首次全量同步。

```java
if (lastCarCapInfo != null) {
    carCapinfoService.SynCarCapInfo(lastCarCapInfo.getCapTime());
} else {
    carCapinfoService.SynCarCapInfo(null);
}
```

实际同步逻辑位于 `CarCapinfoServiceImpl`，调用外部接口：

```java
HttpAPI.GetCarInoutInfo
```

每页默认读取 100 条：

```java
pageSize = 100;
```

接口返回的 `detailList` 会被解析为 `CarCapinfo` 并写入本地。

#### 去重与更新规则

按以下组合查询本地记录：

```text
plateNo + capFlag + capTime
```

- 已存在：更新该记录；
- 不存在：新增该记录。

#### 业务目的

同步外部停车平台产生的车辆进场、出场或抓拍类记录，形成系统本地的车辆进出数据。

#### 数据流

```text
本地最新 capTime
    ↓
外部车辆进出接口（携带 startTime）
    ↓
分页读取 detailList
    ↓
按车牌 + 进出标识 + 时间去重
    ↓
新增或更新 CarCapinfo
```

#### 风险与注意点

1. 同步边界使用最后一条时间，可能产生重复记录；当前通过组合字段去重缓解。
2. 若外部结果并非按时间排序，最后一条本地记录可能不是真正最大时间点。
3. 若外部接口存在延迟到达的数据，可能会漏掉早于 `startTime` 的迟到记录。
4. 批量同步未见完整的任务级事务、失败补偿与统计日志。

### 4. `SynCarListTask`

**入口方法：** `synCarList()`

#### 主要流程

调用外部固定车位车辆卡片列表接口：

```java
HttpAPI.GetCarCardList
```

首次请求获取总条数 `totalCount`，计算总页数；随后按页拉取全部车辆资料：

```java
sumPage = ceil(totalCount / pageSize)
```

默认分页大小：

```java
pageSize = 100;
```

每页请求重新写入时间戳并生成签名：

```java
req.put("ts", System.currentTimeMillis());
req.put("key", SignUtils.paramsSign(req, HttpAPI.appSercert));
```

#### 解析的数据

每个车辆卡片对象会拆解为三类本地实体：

| 外部数据 | 本地实体 | 作用 |
| --- | --- | --- |
| 车辆卡片主对象 | `CarInfo` | 车辆/车主主数据 |
| `plateNoInfo` | `List<CarPlatenoinfo>` | 车牌信息 |
| `carLotList` | `List<CarLot>` | 车位信息 |

最终调用：

```java
iCarInfoTaskService.addCarInfo(carInfo, carPlatenoinfos, carLots);
```

#### 本地同步规则

`CarInfoTaskServiceImpl` 根据 `cardId` 查询本地车辆：

```java
carInfoMapper.getCarInfoByCrdId(carInfo.getCardId())
```

- 本地不存在：新增 `CarInfo`，并同步关联车牌、车位；
- 本地存在且 `lastUpdateTime` 变化：更新主信息，并同步关联车牌、车位；
- 更新时间未变化：不处理。

#### 业务目的

这是停车业务的基础数据同步任务，用于将外部停车平台中的固定车位、车辆、车牌及使用人信息同步到本地系统。

#### 数据流

```text
外部固定车位车辆列表
    ↓
CarInfo（车辆/使用人）
    ├── CarPlatenoinfo（车牌）
    └── CarLot（车位）
```

#### 风险与注意点

1. 仅处理新增和更新，没有处理外部删除的车辆、车牌或车位。
2. 分页期间外部数据变化时，可能产生漏同步或重复同步。
3. 代码打印完整接口响应及每条车辆信息，可能泄露电话、姓名、车牌等敏感数据。
4. 类中的 `totalCount` 成员变量没有被实际使用，存在遗留代码。
5. `main()` 方法仅为测试用途，与任务无关。

### 5. `SynHikUserTask`

**入口方法：** `SynHikUser()`

#### 主要流程

1. 从系统字典类型 `guard_info` 中读取门禁设备 IP 列表：

   ```java
   iSysDictDataService.selectDictValueUseDictType("guard_info")
   ```

2. 实际仅使用列表第一项 IP：

   ```java
   String ip = ips.get(0);
   ```

3. 使用海康 SDK 登录设备：

   ```java
   EntranceguardAPI.SKDLogin(ip, "admin", "hik12345");
   ```

4. 读取设备中全部卡片用户：

   ```java
   List<AEntranceguard> users = EntranceguardAPI.getAllCard();
   ```

5. 按 `user_id` 判断本地是否已存在；仅当不存在时：
   - 下载用户人脸图片；
   - 写入 `faceImg` 图片地址；
   - 新增本地门禁用户记录。

6. 在 `finally` 中退出登录并清理 SDK：

   ```java
   EntranceguardAPI.logout();
   EntranceguardAPI.CleanSDK();
   ```

#### 业务目的

将海康门禁设备中的卡片用户及人脸照片同步到本地 `AEntranceguard` 数据中。

#### 数据流

```text
系统字典 guard_info
    ↓
海康门禁设备 IP
    ↓
读取设备全部卡片用户
    ↓
按 user_id 判断本地是否存在
    ↓
下载人脸图片并插入 AEntranceguard
```

#### 风险与注意点

1. 海康设备账号密码 `admin / hik12345` 硬编码，安全风险较高。
2. 虽然读取了多个 IP，但实际只同步第一个设备。
3. 文件末尾遍历 IP 的代码为空，不产生任何作用，属于遗留逻辑。
4. 仅新增本地不存在的用户，不会更新已有用户的卡号、姓名、人脸或状态。
5. 未清理设备端已删除、但本地仍存在的用户。
6. 异常仅 `printStackTrace()`，没有统一日志、失败统计或告警。

### 7. `SyVioDischargePunishmentTask`

**入口方法：** `dischargePunishment()`

#### 主要流程

1. 读取黑名单处罚时长配置：

   ```java
   configService.selectConfigByKey("blacklist.remove.time")
   ```

2. 查询全部违章积分统计记录：

   ```java
   vioScoreStatisticsMapper.getVioScoreStatisticsList()
   ```

3. 对有处罚时间 `vioPunishmentTime` 的记录，判断是否已超过处罚期限。
4. 到期后按车牌查找黑名单记录。
5. 调用 `vioBlacklistService.delete(id)` 解除黑名单；若成功，再删除积分统计记录。

#### 到期判断规则

解除日期计算：

```java
punishmentTime + Integer.parseInt(removeTime) 天
```

最终判断：

```java
LocalDate.now().isAfter(localTime)
```

这意味着只有当前日期**晚于**解除日期时才会解除。例如处罚开始日期为 2026-08-01、处罚天数为 30 天，则解除日期为 2026-08-31，实际会在 2026-09-01 起被任务解除，而不是 2026-08-31 当天。

#### `vioBlacklistService.delete()` 的实际行为

解除黑名单并非只删除一条本地数据。其处理流程为：

1. 根据黑名单车牌查询车辆和车牌信息；
2. 读取车辆原始区域 `originalAreaId`、`originalAreaName`；
3. 将车辆车位恢复至原始区域；
4. 调用外部停车平台接口 `KeyTopApiUtil.modifyCarCardNo(...)` 恢复车辆卡片/车位信息；
5. 更新本地车辆与车位数据；
6. 删除违章积分统计；
7. 删除本地黑名单记录。

#### 业务目的

在违章处罚期限届满后，自动把车辆从黑名单状态恢复，恢复其原始停车区域，并同步外部停车平台状态。

#### 数据流

```text
违章积分统计
    ↓
处罚时间 + blacklist.remove.time
    ↓
处罚到期判断
    ↓
查询黑名单车辆
    ↓
恢复车辆原始区域
    ↓
同步外部停车平台车辆卡片
    ↓
删除黑名单与违章积分统计
```

#### 风险与注意点

1. `blacklist.remove.time` 为空或非数字时，任务会抛出异常。
2. 到期日当天不会解除，可能比预期多处罚一天。
3. `vioBlacklistService.delete()` 内部已删除积分统计，任务外层又删除一次，存在重复删除。
4. 外部平台恢复失败时，本地黑名单不会被删除；这可保持状态一致，但没有失败次数、人工补偿和告警机制。
5. 黑名单解除、外部同步、积分删除之间未见统一事务边界，可能发生部分成功。

## 三、任务间的业务关系

这些任务大体构成以下业务链路：

```text
同步停车区域
    └── area_type 系统字典

同步固定车位车辆数据
    ├── CarInfo（车辆/使用人）
    ├── CarPlatenoinfo（车牌）
    └── CarLot（车位）
            │
            └── 自动生成平台账号

同步车辆进出记录
    └── CarCapinfo

同步海康门禁用户
    └── AEntranceguard（用户及人脸）

车辆违章积分累计
    ├── 达到积分阈值后加入黑名单
    ├── 将车辆车位调整到“大门”区域
    └── 处罚期届满后恢复原区域并解除黑名单
```

违章处罚的核心逻辑位于 `VioScoreStatisticsServiceImpl.scoreStatistics()`：当累计积分达到配置阈值时，调用：

```java
vioBlacklistService.add(vioPlateNo);
```

加入黑名单时，车辆关联车位会被调整为：

```java
areaName = "大门";
areaId = "4";
```

处罚到期后，`SyVioDischargePunishmentTask` 会恢复此前保存的原区域信息。

## 四、建议重点核查项

### 1. 任务调度配置

当前任务类没有 `@Scheduled` 注解，应继续确认：

- Quartz 任务配置；
- `sys_job` 等数据库任务表；
- 后台定时任务管理页面；
- 是否通过反射按“Bean 名称 + 方法名”执行。

重点关注各任务的 Cron、启停状态、并发执行策略及失败重试策略。

### 2. 敏感配置治理

以下信息不应硬编码在源码中：

- 自动生成账号默认密码；
- 海康门禁设备账号密码；
- 固定部门 ID、角色 ID；
- 外部平台签名密钥。

应改为受控配置，并为初始账号提供强制修改密码、首次登录重置或短信激活机制。

### 3. 外部数据的删除/失效同步

当前多数同步任务仅做新增和更新，建议明确并补齐：

- 外部车辆取消后的本地处理；
- 外部门禁用户删除后的本地处理；
- 外部区域废弃后的字典处理；
- 外部车牌、车位变更后的关联数据清理策略。

### 4. 任务可观测性与补偿机制

建议为同步任务增加：

- 统一业务日志；
- 拉取总量、成功量、失败量；
- 同步开始/结束时间与耗时；
- 外部接口错误码、失败原因；
- 可追踪的断点/游标；
- 有限重试、告警和人工补偿入口。

### 5. 黑名单解除一致性

黑名单解除依赖外部停车平台恢复车辆卡片成功。建议核查：

- 外部接口超时、失败、重复提交的处理；
- 本地黑名单、积分统计、车辆区域三者的一致性；
- 积分统计被重复删除的问题；
- 解除日期是否应使用“当天到期即解除”的 `!now.isBefore(expireDate)` 语义。

## 五、结论

这 7 个任务可归为四类：

1. **基础资料同步**：`SynAreaInfoTask`、`SynCarListTask`；
2. **运行数据同步**：`SynCarCapInfoTask`；
3. **门禁数据同步**：`SynHikUserTask`；
4. **账号与违章管理**：`SynAccountGenerateTask`、`SynVioBlackTask`、`SyVioDischargePunishmentTask`。

其中最关键的业务闭环是：

```text
车辆资料同步
    → 违章积分累计
    → 达到阈值进入黑名单并转至“大门”区域
    → 处罚到期
    → 恢复原区域并解除黑名单
```

当前优先建议确认：任务的实际调度配置、空实现的 `SynVioBlacklist()` 是否应补充、硬编码凭据是否仍在使用，以及黑名单解除流程是否具备足够的一致性与失败补偿能力。
