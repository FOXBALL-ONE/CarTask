# 车辆进出记录图片下载调度方案

## 1. 文档信息

- 状态：待实施
- 适用任务：车辆进出记录同步任务 `car_cap_info.sync`
- 相关代码：`SynCarCapInfoTask`、`FileService`、`KeytopProperties`
- 目标：支持调整图片下载间隔和并行下载数，同时保证记录不丢失、失败可重试、检查点不错误推进

## 2. 背景与现状

当前车辆进出记录同步流程位于 `SynCarCapInfoTask`，主要流程如下：

1. 按检查点计算查询时间范围。
2. 分页调用科拓车辆进出接口。
3. 在 `processRecords` 中逐条解析和保存车辆进出记录。
4. 对每条记录同步调用 `FileService.importRemote` 下载抓拍图片。
5. 图片下载完成后保存本地文件地址和图片同步状态。
6. 整个增量范围成功后推进 `SyncCheckpoint`。

目前图片下载具有以下限制：

- 图片下载与记录写入在同一条串行流程中，整体耗时受图片数量和远程响应时间影响。
- 没有独立的下载并行度配置，无法根据科拓接口承载能力调节压力。
- 没有下载启动间隔控制，短时间内可能集中发起大量图片请求。
- `FileService.importRemote` 会执行远程 HTTP 请求、落盘和文件元数据写入，不能简单地把共享 JPA 实体放入多个线程并发修改。
- 当前全局 `executionLock` 应继续保证增量同步和补偿同步互斥；本方案只并行图片下载，不并行多个同步任务。

## 3. 设计目标

### 3.1 必须满足

- 支持配置全局图片下载启动间隔。
- 支持配置同时进行的图片下载数。
- 分页接口请求仍然串行，避免上游分页数据变化造成漏数或重复放大。
- 图片下载失败不阻断其它车辆记录的入库。
- 应用重启或同步中断后，待下载和失败图片可以继续重试。
- 检查点只在记录分页处理完成后推进，不因图片并发而提前推进。
- 同一条记录在同一轮同步中最多提交一个图片下载任务。
- 不新增数据库迁移脚本。

### 3.2 非目标

- 本期不并行拉取科拓车辆进出分页数据。
- 本期不改变车辆记录的去重规则和检查点规则。
- 本期不对 `FileService` 做图片内容去重改造。
- 本期不实现多实例之间的全局限速；多实例部署时需要另行增加分布式限流。

## 4. 配置设计

### 4.1 配置项

在 `KeytopProperties` 增加以下配置：

```yaml
keytop:
  car-cap-info-photo-download-interval: ${KEYTOP_CAR_CAP_INFO_PHOTO_DOWNLOAD_INTERVAL:200ms}
  car-cap-info-photo-download-concurrency: ${KEYTOP_CAR_CAP_INFO_PHOTO_DOWNLOAD_CONCURRENCY:4}
```

配置语义：

| 配置 | 类型 | 默认值 | 建议范围 | 说明 |
| --- | --- | --- | --- | --- |
| `carCapInfoPhotoDownloadInterval` | `Duration` | `200ms` | `0ms` 至 `60s` | 全局两次图片下载请求的最小启动间隔 |
| `carCapInfoPhotoDownloadConcurrency` | `Int` | `4` | `1` 至 `16` | 同时进行的图片下载数 |

下载间隔应定义为“下载请求开始时间之间的最小间隔”，而不是请求完成时间之间的间隔。例如：

- 间隔为 `200ms` 时，所有下载请求的启动时间至少相隔 200 毫秒。
- 并行数为 `4` 时，最多 4 个请求处于下载中。
- `0ms` 表示不主动限速，但仍受并行数限制。

实际吞吐量约为：

```text
min(并行下载数 / 平均单次下载耗时, 1 / 下载启动间隔)
```

### 4.2 配置校验

在 `KeytopProperties` 初始化时校验：

- 下载间隔不能为负数。
- 下载并行数必须在 `1..16`。
- 下载间隔不能超过 60 秒。
- 原有的分页大小和回看窗口校验保持不变。

### 4.3 配置调整方式

第一版复用现有系统配置能力，不新增配置表：

1. 将两个环境变量加入 `SystemConfigService` 的可编辑白名单。
2. 在系统配置页增加两个字段。
3. 保存时写入 `.env`。
4. 按现有流程重载服务后生效。

配置属性在应用启动时绑定，因此配置保存后必须重载服务；正在执行的同步可能被重启中断。应在页面上明确提示，建议在当前同步完成后再重载。

每次同步开始时读取并固定本次运行的配置快照。重载后启动的新任务使用新值，已经开始的任务不动态改变线程池大小或限速参数。

## 5. 推荐架构

### 5.1 分层流程

将当前“解析记录、下载图片、保存记录”拆分为以下阶段：

```text
拉取一页记录
    -> 解析记录并完成去重
    -> 保存记录元数据
    -> 生成图片下载任务
    -> 使用有界下载协调器并行下载
    -> 更新图片状态和本地地址
    -> 等待本页图片任务完成
    -> 拉取下一页
```

推荐按页设置同步屏障：一页记录入库并完成该页图片任务后，再处理下一页。这样可以限制内存中的任务数量，也能保持现有进度统计和错误处理语义，避免一次性把整个时间范围的图片任务全部提交到线程池。

### 5.2 图片下载任务

不要把 `AccessRecord` JPA 实体直接交给线程池。任务只携带不可变值：

```text
recordId
sourcePhotoUrl
plateNumber
```

下载线程完成后通过 `recordId` 重新读取记录，再使用独立的 Repository 调用更新结果。这样可以避免多个线程共享同一个 Hibernate 实体实例，也避免跨线程持有原同步线程的持久化上下文。

### 5.3 独立下载执行器

新增专用的图片下载线程池，例如 `vehiclePhotoDownloadExecutor`：

- 固定线程数等于 `carCapInfoPhotoDownloadConcurrency`。
- 使用独立线程名前缀 `vehicle-photo-download-`。
- 不复用 `syncTaskScheduler`，避免图片下载占满定时任务调度线程。
- 使用有界队列，禁止无限制堆积图片任务。
- 应用关闭时等待正在进行的下载在限定时间内结束。

下载协调器负责向执行器提交任务、执行限速、收集结果和处理异常。单个图片失败只能影响该图片，不应让同页其它图片任务被取消。

### 5.4 全局启动间隔限速

限速器属于下载协调器实例，所有下载线程共享同一个时间序列：

1. 下载线程申请下一个启动时间。
2. 限速器原子地预留时间槽。
3. 线程在锁外等待到预留时间。
4. 到达时间后调用 `FileService.importRemote`。

等待不能持有限速锁，否则会使其它线程无法申请时间槽。限速器应使用 `System.nanoTime()` 计算间隔，避免系统时间回拨导致等待异常。

当前应用按单实例部署设计，因此该限速器只保证单实例内的间隔和并行度。若以后部署多个后端实例，需要将限流和并发控制移到 Redis 或网关层，不能仅依赖本地线程池。

## 6. 图片状态与失败恢复

### 6.1 状态流转

建议在 `AccessRecord.PhotoSyncStatus` 增加 `PENDING`：

```text
无图片地址       -> NOT_AVAILABLE
有图片地址待下载 -> PENDING
下载成功         -> LOCAL
下载失败         -> FAILED
```

`photoUrl` 在下载成功前可以保留源地址作为展示兜底；下载成功后替换为本地文件下载地址。`sourcePhotoUrl` 始终保存上游地址，用于判断图片是否发生变化和后续重试。

增加枚举值不会要求新增迁移脚本；该字段当前使用字符串枚举存储。部署前仍需确认目标数据库没有额外的枚举约束。

### 6.2 新记录处理

对于有远程图片地址的新记录：

1. 先保存记录元数据和 `PENDING` 状态。
2. 提交图片下载任务。
3. 下载成功后更新为 `LOCAL`。
4. 下载失败后更新为 `FAILED` 并保存截断后的错误信息。

对于没有图片地址的记录，直接保存为 `NOT_AVAILABLE`，不提交下载任务。

### 6.3 已有记录处理

- 上游图片地址未变化且本地状态为 `LOCAL`：跳过下载。
- 上游图片地址变化：更新源地址并重新设置为 `PENDING`。
- 状态为 `FAILED` 或 `PENDING`：加入重试队列。
- 记录已经被删除：下载完成后更新时忽略，不应使整批任务失败。

现有 `retryFailedPhotos()` 应改为通过同一个下载协调器处理，并限制单次重试数量，防止历史失败图片长期占满当前同步任务。

### 6.4 同步中断

同步被中断时：

- 已保存的车辆记录不会回滚。
- `PENDING` 图片在下一次同步中继续处理。
- 已标记 `FAILED` 的图片按重试策略再次处理。
- 增量检查点只有在当前范围完整处理后才推进，因此不会因为图片并发提前跳过未处理的记录。
- 任务捕获中断异常时应恢复线程中断标记，并保证线程池任务不会继续提交新的下载。

## 7. 检查点、幂等和并发边界

### 7.1 检查点

检查点仍由同步主线程管理：

```text
同步开始 -> RUNNING
每页记录和图片任务完成
同步范围全部完成 -> SUCCESS 并推进 cursorTime
发生不可恢复的同步错误 -> FAILED，不推进 cursorTime
```

单张图片失败不属于分页接口失败，不应阻止检查点推进；失败图片通过 `FAILED` 状态和后续重试恢复。

### 7.2 记录幂等

- 记录入库仍使用 `sourceRecordId` 和现有身份字段去重。
- 同一页内用 `sourceRecordId` 去重后再创建图片任务。
- 同一轮运行中维护 `recordId` 集合，避免同一记录重复提交图片任务。
- 数据库唯一约束仍是最终防线，不能依赖线程池内存去重替代数据库约束。

### 7.3 任务互斥

现有 `executionLock` 保留，确保：

- 增量同步和补偿同步不能同时运行。
- 手动同步和定时同步不能重叠。
- 同一时间只有一个车辆进出记录同步流程拥有图片下载协调器。

并行下载只发生在同一同步流程内部，不改变任务级互斥规则。

## 8. 接口与前端调整

### 8.1 推荐复用系统配置接口

第一版不新增专用数据库配置接口，直接扩展现有 `/api/system/config`：

- `GET /api/system/config` 返回两个新增环境变量的当前值。
- `PUT /api/system/config` 接收现有 `values` 配置集合。
- `POST /api/system/config/reload` 继续负责使配置生效。

系统配置接口已有统一请求结构，新增字段沿用现有实现，不再创建重复的配置 DTO。

### 8.2 前端显示

在系统配置页增加：

- 图片下载间隔输入框，显示毫秒或 Spring `Duration` 格式。
- 图片并行下载数输入框，限制为 1 到 16。
- “保存后需要重载服务”的提示。
- 当前同步运行时显示本次任务使用的下载配置。

车辆进出同步卡片可以继续显示现有记录进度，同时补充以下统计：

- 图片下载成功数。
- 图片下载失败数。
- 待处理图片数。

这些统计优先放入内存进度快照和日志，不新增历史表字段。

### 8.3 若后续需要免重启调整

免重启调整不应直接修改 `@ConfigurationProperties` Bean。后续可以增加一个线程安全的运行时设置服务：

- 启动时从 `KeytopProperties` 初始化。
- 管理接口校验后更新 `AtomicReference`。
- 新同步任务读取设置快照。
- 下载执行器采用任务级并发控制，不能在运行中直接改变固定线程池大小。

该模式需要补充配置持久化和多实例一致性设计，建议作为第二阶段，不与本期的低风险改造混合实现。

## 9. 日志、监控与历史

每次车辆进出同步开始时记录配置快照：

```text
download_interval
download_concurrency
data_start_time
data_end_time
```

同步结束时记录：

- 提交图片任务数。
- 成功下载数。
- 失败数。
- 无图片地址数。
- 重试数。
- 下载总耗时和平均耗时。

日志中不得记录完整图片地址中的敏感参数。现有 `SyncTaskRun` 的 `localPhotoCount` 和 `failedPhotoCount` 可以继续使用，详细统计先放在 `summary` 和结构化日志中，避免本期扩展历史表结构。

建议增加以下指标：

- `vehicle_photo_download_submitted_total`
- `vehicle_photo_download_success_total`
- `vehicle_photo_download_failed_total`
- `vehicle_photo_download_duration`
- `vehicle_photo_download_inflight`

## 11. 测试方案

### 11.1 单元测试

- 配置为负间隔、0 并行数、超过最大并行数时启动失败。
- `0ms` 间隔不产生额外等待。
- 多线程提交时，实际同时下载数不超过配置值。
- 多线程提交时，下载启动时间满足全局最小间隔。
- 单个下载失败不会取消同页其它任务。
- 下载异常会写入 `FAILED` 和错误信息。
- 下载成功会写入 `LOCAL` 和本地地址。
- 相同记录不会在一轮同步中重复下载。

限速测试应注入可控时钟或时间源，不直接依赖真实 `sleep`，避免测试不稳定。

### 11.2 同步流程测试

- 新记录先保存为 `PENDING`，随后变为 `LOCAL`。
- 图片失败时车辆记录仍然存在，检查点按记录处理规则推进。
- 同步中断后再次执行可以重试 `PENDING` 和 `FAILED`。
- 上游图片地址变化会触发重新下载。
- 增量同步、补偿同步和手动同步仍受同一把执行锁保护。
- 页面总数未知时，最后一页判断逻辑保持正确。

### 11.3 验收场景

使用一批包含成功、超时、404、空图片地址和重复记录的数据进行验证：

1. 配置并行数为 1，确认行为与现有串行逻辑一致。
2. 配置并行数为 4，确认最大同时下载数为 4。
3. 配置间隔为 1 秒，确认下载请求启动时间至少相隔 1 秒。
4. 中途停止服务，确认重启后未完成图片会继续处理。
5. 修改配置并重载，确认新任务使用新参数，历史任务不会继续占用旧线程池。

## 12. 实施顺序

1. 增加配置和校验，先不改变下载行为。
2. 增加专用下载执行器和全局限速器。
3. 将 `SynCarCapInfoTask` 拆成记录阶段和图片阶段。
4. 增加 `PENDING` 状态、失败重试和中断恢复。
5. 接入系统配置页和重载提示。
6. 增加日志、指标和测试。
7. 先使用默认值 `200ms + 4` 灰度运行，再根据科拓响应耗时和失败率调整。

## 13. 风险与处理

| 风险 | 处理方式 |
| --- | --- |
| 并行下载触发科拓或图片服务器限流 | 使用全局启动间隔和并行上限，默认保守配置 |
| 图片下载线程占满定时任务线程 | 使用独立图片下载执行器 |
| 多线程共享 JPA 实体导致数据错乱 | 线程任务只传 ID 和不可变参数，完成后重新查询实体 |
| 应用重启造成图片任务中断 | 使用 `PENDING` / `FAILED` 状态，下次任务重试 |
| 配置重载中断正在运行的同步 | 前端提示等待同步结束后重载，检查点不提前推进 |
| 多实例部署时每台机器各自限速 | 本期明确限制为单实例；多实例时增加 Redis 分布式限流 |
| 线程池任务无限排队导致内存增长 | 按页提交并等待，有界队列和任务数量上限 |
