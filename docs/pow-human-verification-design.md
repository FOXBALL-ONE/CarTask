# POW 人机验证系统设计

## 1. 文档信息

| 项目 | 内容 |
| --- | --- |
| 状态 | 设计稿，待评审 |
| 范围 | 基于工作量证明（Proof of Work，POW）的无感自动验证与手动触发验证 |
| 目标应用 | ShopMall 客户端及其 Spring Boot 后端 |
| 相关现状 | 认证模块已有图形验证码、Redis 和登录限流；本方案设计新增 POW 验证，不表示已经实现 |

## 2. 背景与目标

当前认证流程使用图形验证码阻挡自动化请求。图形验证码要求正常用户识别并输入，增加了登录、短信发送等敏感操作的摩擦。本方案以客户端计算哈希作为基础验证：多数普通请求在后台完成少量计算；计算超时、环境异常或风险升高时，再展示明确的手动验证动作。

目标：

- 默认无感运行，验证完成后不要求用户输入答案或点击额外控件。
- 支持用户主动点击“验证”触发计算，特别适用于无感计算被浏览器限制、页面长期挂起或用户希望显式重试的场景。
- 服务端独立验证工作量，不信任客户端声称的难度、答案或耗时。
- 挑战绑定用途、过期时间和随机数，成功后一次性消费，避免重放与跨接口挪用。
- 能按风险等级增加计算量，并与现有登录失败限流、短信发送冷却等机制叠加。
- 支持渐进式替换图形验证码，先影子验证和灰度，再按接口迁移。

非目标：POW 单独判断人的身份、替代账号密码/短信认证、抵御大规模分布式僵尸网络或提供绝对的机器人识别保证。POW 增加每次请求的成本，但有硬件的攻击者仍可并行计算。

## 3. 设计原则与威胁模型

1. **验证的是可验证工作量**：服务器发出随机挑战，客户端寻找满足哈希前缀条件的 nonce，服务器重算哈希并确认难度。
2. **挑战不能由客户端自选**：challenge ID、随机种子、难度、用途与到期时间由服务器签发并存储。
3. **一次性和用途隔离**：成功验证原子消费挑战；登录挑战不能用于短信发送或重置密码。
4. **POW 不替代限流**：通过 IP、账号、用途、设备信号的现有限流规则控制挑战签发与业务尝试。
5. **难度可运营**：按用途和风险档位配置目标耗时、难度上下界及版本；不能让单一高难度拖垮低端设备。
6. **隐私最小化**：不要求采集指纹、摄像头或行为轨迹；仅以短期 Redis 状态记录验证生命周期和必要的风控计数。

威胁假设包括：直接脚本调用接口、复用旧证明、将某接口证明挪到另一用途、并发提交同一证明、伪造客户端耗时、批量申请挑战消耗服务资源，以及攻击者使用 GPU/多核或代理池。客户端执行环境本身不可信。

## 4. 组件与职责

```text
浏览器/客户端
  ├─ ChallengeRunner：SHA-256 计算、截止时间、取消与进度状态
  ├─ AutoVerifier：后台自动启动，页面隐藏时暂停或取消
  └─ ManualVerifier：由用户点击触发同一计算器
          │ HTTPS
          ▼
Spring Boot 后端
  ├─ PowChallengeController：签发挑战与提交证明
  ├─ PowVerificationService：用途检查、哈希验证、一次性消费
  ├─ PowDifficultyPolicy：基于用途、风险和配置决定难度
  ├─ Pow Redis 状态：挑战 TTL、消费原子性、签发限流
  └─ 认证/业务服务：要求有效的用途证明后执行业务
          │
          ├─ Redis：短期挑战状态与计数
          └─ 现有登录限流、验证码/短信服务及审计机制
```

### 4.1 浏览器组件

- `ChallengeRunner` 复用在自动和手动模式中。算法、输入编码及 nonce 表示必须与服务端一致。
- 可使用 Web Worker 避免主线程冻结；Worker 接收随机种子、challenge ID、难度和截止时间，返回 nonce、摘要和计算轮数。
- 自动模式在挑战签发后立即开始；页面隐藏时暂停并在恢复后续算，超过截止时间则重新取挑战。
- 手动模式由用户按钮启动或重试，展示简洁进度和取消入口。手动点击只是交互入口，不是可信的人类证据；不得仅凭点击放行。
- 计算完成后提交证明。客户端显示结果等待业务继续，不把成功状态长期存入 localStorage；必要的短暂内存缓存按挑战用途隔离。

## 5. POW 协议

### 5.1 算法与编码

一期采用 SHA-256，输入字节串为 UTF-8：

```text
"shopmall-pow:v1:" + challenge_id + ":" + purpose + ":" + seed + ":" + nonce
```

`nonce` 使用十进制无符号整数的规范字符串，从 `0` 递增。客户端与服务端必须采用完全相同的 UTF-8 编码、大小写规则和分隔符。服务端计算 `digest = SHA256(input)`，若摘要开头至少有 `difficulty_bits` 个连续零位，则证明有效。第一个字节为 8 个零位，避免十六进制文本比较产生歧义。

期望尝试次数约为 `2^difficulty_bits`。难度应通过目标客户端 P50/P95 耗时实测标定，初始建议从 18–22 位进行压测和可用性试验，不作为固定生产值。每个用途配置最低、默认、最高难度和服务端计算上限。

### 5.2 挑战状态

签发时服务端用 CSPRNG 生成至少 128 位 `challenge_id` 和 256 位 `seed`。Redis 记录：

| 字段 | 含义 |
| --- | --- |
| `purpose` | 固定用途枚举，如 `LOGIN`、`SMS_SEND`、`PASSWORD_RESET` |
| `seed` | 随机挑战输入 |
| `difficulty_bits` | 本挑战要求的零位数 |
| `issued_at` / `expires_at` | 服务端签发和失效时间 |
| `status` | `ISSUED`；成功消费后删除或标记 `CONSUMED` |
| `policy_version` | 便于难度策略变更和问题追踪 |

挑战 TTL 建议 2 分钟；具体值由低端设备计算时长和接口安全窗口验证后定稿。Redis key 使用带版本和用途前缀的随机 ID，不将账号、手机号或原始 IP 写入 key。签发接口也需限流，限制每 IP/会话并发有效挑战数和全局存量。

### 5.3 验证规则

服务端以 Redis Lua 脚本或等价事务实现原子校验和消费：

1. 挑战必须存在、未过期且状态为 `ISSUED`。
2. 请求用途必须和存储用途相同。
3. 请求难度版本不由客户端覆盖，服务端从存储状态读取。
4. nonce 格式和长度受限，禁止负数、前导零歧义、超长输入；请求总大小设置上限。
5. 服务端重算摘要并检查难度；任何校验失败都不签发业务凭据。对格式错误、用途错误、过期、无效摘要返回统一的外部错误类别，避免泄露挑战状态细节。
6. 成功后原子消费挑战，阻止并发重放。提交成功但业务请求失败时，证明不复用，客户端需获取新挑战。
7. 对相同挑战重复提交一律拒绝；需要处理网络重试时由调用方重新取挑战，而不缓存成功证明作为通用票据。

### 5.4 HTTP 接口草案

接口路径为提案，可结合当前 `/api/auth` 路由风格评审。所有接口强制 HTTPS，响应设置 `Cache-Control: no-store`。

#### 签发挑战

```http
POST /api/verification/pow/challenges
Content-Type: application/json

{"purpose":"LOGIN","mode":"AUTO"}
```

```json
{
  "challenge_id": "随机标识",
  "purpose": "LOGIN",
  "seed": "base64url 随机值",
  "difficulty_bits": 20,
  "expires_at": "2026-09-29T12:00:00",
  "algorithm": "SHA-256",
  "protocol_version": 1
}
```

`mode` 只用于观测产品交互，不参与安全判断；后端不因客户端声称 `MANUAL` 而降低难度。

#### 提交证明

```http
POST /api/verification/pow/verify
Content-Type: application/json

{"challenge_id":"...","purpose":"LOGIN","nonce":"154722"}
```

成功响应只表示挑战已验证并消费，返回用途受限的短时 `verification_token`：

```json
{"verification_token":"短时不透明票据","expires_at":"2026-09-29T12:00:30"}
```

令牌应至少绑定用途、挑战 ID、签发时间和唯一随机数，建议存储在 Redis 并只允许使用一次，TTL 建议不超过 30 秒。它不得作为登录态或独立通用授权。业务端点消费票据必须与业务操作的鉴权流程保持原子边界；若无法在一次 Redis 事务中安全消费，则将证明字段随业务请求提交，并在认证服务内部完成验证和挑战消费。

#### 业务请求接入

登录密码请求携带用途为 `LOGIN` 的票据/证明；短信发送携带 `SMS_SEND`；重置密码携带 `PASSWORD_RESET`。服务端忽略未知用途，禁止跨用途复用。当前图形验证码使用处（密码登录、短信发送等）逐个迁移，不应一次删除现有图形验证码。

## 6. 自动与手动流程

### 6.1 无感自动验证

```text
页面进入敏感操作上下文
  → 请求对应 purpose 的挑战
  → 后端按策略签发 seed / difficulty / expiry
  → Web Worker 自动寻找 nonce
  → 到达 nonce 后提交验证
  → 将短时用途票据附加到目标业务请求
  → 后端消费票据后继续既有账号/业务校验
```

正常情况下不显示验证码或新增确认步骤。不得在页面加载时对所有访客预热无限挑战；仅在进入登录、短信发送等真实操作上下文时签发。

### 6.2 手动点击验证

```text
自动计算未开始/超时/被浏览器挂起
  → 显示“点击验证并继续”控件
  → 用户点击后取新挑战或续用仍有效挑战
  → 通过同一 Web Worker 计算
  → 展示进行中、完成、超时、重试和取消状态
  → 验证成功后继续原操作
```

手动模式不能要求用户解算图片或完成行为谜题；触发操作必须有键盘可达性、屏幕阅读器状态和可取消能力。若设备无法完成 POW，应提供受策略限制的替代通道（现阶段保留图形验证码或短信/人工支持策略），并记录回退原因，不能静默跳过验证。

### 6.3 超时与错误

- 挑战过期：自动取新挑战并重算，最多自动重试一次，之后给出手动重试控件。
- 页面隐藏、导航或组件销毁：取消 Worker；回到页面时检查剩余时间。
- 浏览器不支持 Web Worker 或 SHA-256：显示可访问的手动重试/现有验证码回退，不降低服务器校验要求。
- Redis 不可用：敏感操作失败关闭；由运维恢复 Redis，或使用受控的现有验证码降级开关。不得在 Redis 故障时默认放行。
- 业务端点失败：POW 票据已使用则重新签发；保留当前登录失败次数、短信冷却和审计语义。

## 7. 难度与风控策略

`PowDifficultyPolicy` 依据用途和服务端可观测信号决定档位，至少包括：

- 用途基线难度及上下限；
- IP/网段短时签发速率、失败率及活跃挑战数；
- 登录账号哈希维度的失败次数（不能通过不存在账号与真实账号响应泄漏）；
- 同一会话/匿名客户端短期挑战频率；
- 全局负载与验证队列健康度。

风险升高时逐步提高难度或切换显式验证/现有 CAPTCHA；达到硬阈值时由既有限流直接拒绝。难度策略必须有最高值及客户端最大耗时门槛，并支持配置快速回滚。IP 仅作为弱信号，须考虑 NAT 和可信代理头配置；禁止直接信任任意 `X-Forwarded-For`。

POW 失败、挑战请求和业务认证失败分别计数，避免攻击者用错误 POW 无限消耗密码失败额度，也避免通过大量低成本挑战绕过登录限流。指标使用用途、难度档、耗时区间和结果，不记录 nonce、seed、口令、短信验证码或完整票据。

## 8. 安全、隐私与可用性要求

- **重放**：一次性挑战消费必须原子化；测试并发提交同一 nonce，只允许一个成功。
- **跨站和跨用途**：结合现有 CORS/CSRF 策略；challenge 与 proof 均绑定 purpose，来源检查只作为纵深防御。
- **资源耗尽**：限制挑战签发、Redis key 数量、请求体大小、nonce 长度、并发 Worker 和计算时间；服务端对每次校验仅执行一次哈希。
- **伪造耗时/客户端**：不采信客户端报告的 duration、attempts 或 UA；难度与有效性完全由服务端决定。
- **代理转算/农场**：POW 无法阻止证明外包或预先计算收益；高风险操作仍需账号认证、业务限流和其他证据。
- **浏览器能耗**：计算设明确截止时间，可取消；后台标签不持续占用 CPU；按设备端实测选择可接受的目标耗时。
- **隐私**：不引入持久设备指纹；日志不存个人敏感输入。挑战 TTL 后 Redis 自动清理。
- **响应差异**：无效、过期、已消费挑战向匿名客户端提供统一错误语义，具体诊断通过低敏感度指标统计。
- **配置安全**：生产环境禁用绕过开关；灰度、降级与难度变更均需审计配置来源及操作者。

## 9. 兼容与迁移

当前 `/api/auth/login` 与短信发送命令接收图形验证码 token/answer，登录服务会在校验验证码后执行账号限流和凭据校验。迁移需同步调整 API 契约、认证服务、登录页状态、短信发送路径和测试。

建议顺序：

1. **基线测量**：记录现有验证码失败率、认证接口负载、Redis 延迟；对目标浏览器和低端移动设备跑 SHA-256 基准。
2. **协议实现与测试**：先加入挑战签发/验证服务和协议测试，暂不改变业务放行逻辑。
3. **影子模式**：前端获取并计算 POW，后端统计结果，但仍要求图形验证码；比较各设备耗时、失败率及 Redis 成本。
4. **内部灰度**：仅内部账号切到“POW + CAPTCHA”；确认重放、超时、辅助访问和降级路径。
5. **小流量替换**：按用户比例/用途启用无感 POW；对高风险流量仍可要求现有 CAPTCHA。
6. **扩大与清理**：指标稳定后扩大；再单独评审移除图形验证码及相关接口，不能在第一阶段一并删除。

每一步都有服务端开关，关闭 POW 后回到图形验证码验证；客户端不得通过参数自行请求无验证模式。现有登录限流、短信冷却、审计日志保持生效。

## 10. 可观测性与运维

建议指标：

- `pow_challenge_issued_total{purpose,difficulty_bucket}`
- `pow_verify_total{purpose,result}`
- `pow_compute_duration_seconds{purpose,mode_bucket}`（仅客户端可选遥测聚合；不可用作可信安全信号）
- `pow_verify_server_duration_seconds{purpose}`
- `pow_challenge_active`、Redis 操作延迟、签发限流拒绝数
- 回退率、自动转手动比例、浏览器不支持比例、每用途业务成功率

告警关注 Redis 错误率/延迟、挑战存量异常增长、验证成功率骤变和回退比例异常。日志只使用挑战 ID 的短哈希及 trace ID；不记录完整挑战材料。

运维配置至少包括：启用状态、影子/灰度比例、用途白名单、每用途基线/上下限、挑战 TTL、短时票据 TTL、签发限流、手动回退策略。生产参数在测试环境和真实设备基准后确定，不在代码中散布魔法数字。

## 11. 验收标准

- 协议测试覆盖摘要输入规范、正确/错误 nonce、位难度边界、过期、用途不匹配、格式错误和未知版本。
- 两个并发请求提交同一挑战时最多一个成功；成功挑战在任何实例上均不可重放。
- 过期挑战、无效工作量和跨用途证明均不能触发目标业务操作。
- 自动模式无需点击或输入；隐藏标签不持续计算；超时后可点击重试并能取消。
- 手动模式在鼠标、键盘和屏幕阅读器状态下可用；不能以点击本身绕过 POW。
- 目标设备和浏览器达到评审确定的 P50/P95 计算耗时与成功率目标；设备样本包括低端手机。
- 挑战签发及 Redis key 数量受限；压力测试证明异常请求不会造成无界存储或明显拖垮认证服务。
- Redis 故障、灰度回滚和现有 CAPTCHA 回退流程可验证；无验证放行路径不可由匿名客户端构造。
- 现有登录失败锁定、短信冷却、认证审计和错误语义测试继续通过。

## 12. 待评审决策

1. 首批接入用途：仅密码登录，还是连同短信发送、密码重置一并接入？建议先密码登录与短信发送，重置密码后续单独灰度。
2. POW 票据边界：在验证接口换取一次性短时票据，还是把 proof 直接放入业务请求并在服务内部消费？建议先选后者以减少跨接口重放和额外状态。
3. 目标用户设备的计算耗时预算、可接受的无感失败率及低端设备基线是什么？
4. 高风险/不支持设备保留现有图形验证码多久，以及是否需要短信/人工支持替代通道？
5. 难度策略使用哪些现有可靠信号，及其运维配置由谁管理？

这些决策确认后，再形成实现拆分、接口定稿和风险阈值基准；本文不包含数据库迁移脚本或实现改动。
